# MR 评审与原则邮件

交付两种内容：MR 评论解释本提交的具体缺陷；邮件提炼作者下次开发其他功能也能使用的简单原则。不要把邮件写成当前缺陷修复清单或冗长防复发方案。

## 范围与授权

- 先识别用户要草稿、复核还是发布。仅“评审、准备评论、写邮件”不授权外发；明确“发评论、发邮件”则可在同次任务中直接完成，不重复征求已经给出的授权。
- 续接已有任务时，先读取已有 findings、复核结论和发送回执；同一 SHA 的有效证据可以复用，不因进入发布阶段重跑全仓审查或重复发送。
- 创建或调用技能本身不授权外发，也不授权修代码、修改 CRM/权限、部署或合并。
- 确认 MR 的实际目标分支。客户定制线若独立交付，不以回合主线、通用化或主线架构对齐为要求。
- 确定作者和收件人，不写死人名、邮箱、项目、MR 编号或 SMTP 密钥。用户指定地址优先；否则可使用已核实的作者地址。多个地址冲突、提交作者与 MR 作者不一致或只有 noreply 地址时，先问清收件人，并继续独立的审查/评论工作。

## 审查与新旧归因

1. 读取适用仓库指令，核对 cwd、branch、HEAD、worktree 和 dirty 状态。通过 GitLab 获取 source/target、`diff_refs`、作者、已有评论和 CI 状态，固定 base/head；不要默认用 master 作基线。
2. 当前目录不在候选提交或有无关改动时，用固定 head 的隔离 worktree/归档副本读取和验证。检查完整调用链，测试在隔离环境运行；没有外部授权不调用真实 provider。
3. 每条正式 finding 给出稳定 ID、优先级、当前 diff 行、触发条件、可观察影响、代码/反例证据、修复方向及行为验收。尝试寻找已有恢复路径、后端约束等反证，避免把局部退化写成整个能力不可用。
4. **逐条与 base 比较并分类：**
   - 本次直接新增：新逻辑、新对象适配或新功能必要链路缺失。
   - 新入口触发旧缺陷：旧公共代码已有弱点，本次新增可达输入/路径；评论只归因新增集成缺口，说明底层缺陷原已存在。
   - 纯历史问题：base 中已有同样故障链且本次没有新增触发/影响；另列，不混入本 MR 阻断清单。
   - 证据不足：保留为 candidate/待核验，不宣称已确认。
5. 不因文件是新增就认定根因全新，也不因复用了旧函数就认定缺陷全是历史。新功能在 base 不存在，不能把其测试无法在 base 运行解释成 base passed。
6. mock、本地断言、浏览器、provider-live 分别报告。CI 排队超时、skipped 与代码断言失败分开；没有同环境 base/head 失败集合对比，不宣称无新增回归。

## 独立复核与跨模型审查

- 当用户要求“审查”或执行独立复核时，默认同时并行发起 **[`codex-review`](../codex-review/SKILL.md) 与 [`opus-review`](../opus-review/SKILL.md)**（均使用各自默认配置）进行独立审查；若改动足够复杂、双路存在分歧或主控（Controller）信心不足，主控可自主启用 [`dsh-review`](../dsh-review/SKILL.md) 作为第三路独立审查。
- **独立审查，严禁预设主控立场**：传入的审查 prompt 只提供客观 `repo`、`base..head` 范围与上下文事实，不预设主控立场或引导结论；若复核已有 findings，要求独立逐条返回 confirmed / partially_confirmed / rejected / insufficient_evidence 及客观依据。禁止递归审查和实现修改。
- **不可用自动补位**：默认双路中若 Codex 或 Opus 任一方不可用，自动启用 [`dsh-review`](../dsh-review/SKILL.md) 补位以尽量保持双路审查（若仅单指一方且不可用，则自动切至另一可用方）。
- 保存原始结果，主审再核验分歧。读代码认可反例不等于另跑了一遍测试；超时或空结果不算通过。不要直接照抄与失败恢复目标冲突的修复建议。

## 两种交付的写法

**MR 评论：** 每条聚焦一个故障链，标注归因、影响边界与验收。明确缺陷和外部验收缺口分开。已有恢复入口必须写出来。总评绑定 SHA，概括结论与验证边界，不以作者用了什么级别的 Agent 作为批评理由。

**原则邮件：** 中文优先，默认标题加正文不超过 500 字，用户另有长度要求时遵从。称呼作者、用一句话说明背景，再写少量可迁移原则。无需在邮件中重复行号、finding ID、实现细节或本次修复步骤。可以从这些方向中选与证据有关的内容，不机械凑齐五条：

- 复用前确认原有前提和业务边界仍成立。
- 设计成功、失败、取消、重试、退出后的完整生命周期。
- 区分界面状态与业务事实，考虑刷新和重新进入后的恢复。
- 校验先于状态变化，异常后保留输入并恢复可操作性。
- 按用户操作顺序和跨入口行为验证，而不只是按代码结构写测试。

没有具体缺陷也不编造教训；邮件可以说明本次结论与适用的验证原则。语气平等、简洁，不训话、不对作者或模型贴能力标签。

## 发布和发送

授权范围已明确后读取 [references/delivery.md](references/delivery.md)。它包含 GitLab 行内评论、JSON Content-Type、去重/回读和 `ali_mail_` SMTP 操作方式。

- 外发前重新检查 MR head；变更时复核受影响 findings，不发布过期行号。
- 发评论与发邮件是两项独立完成状态：一项阻塞不妨碍另一项已授权、信息充分的工作。
- 使用邮件 helper 默认预览：`python3 <skill-dir>/scripts/send_mail.py --draft <draft.json>`。只有用户明确授权时才加 `--send --receipt <receipt.json>`。脚本参数不是授权来源。
- 外发结果必须有证据：GitLab 回读正文/行号、SMTP accepted 回执。SMTP accepted 不代表进入收件箱或已读；网络中断导致结果未知时禁止盲目重发。
- 最后给出评论链接、邮件收件人/主题及实际状态。未修改实现；临时审查环境按归属和干净状态核对后清理。
