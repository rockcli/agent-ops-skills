# 三方无偏盲审、防过度设计评估与双写赛马

## 核心纪律与模型边界

1. **默认双路独立发起与按需第三路（使用各自默认配置）**：
   - 当用户说“审查方案 / 问一下其他两个 Agent / 请外部审查”时，默认将 **[`codex-review`](../codex-review/SKILL.md) / [`codex-task`](../codex-task/SKILL.md)（Codex 默认配置）与 [`opus-review`](../opus-review/SKILL.md) / [`opus-task`](../opus-task/SKILL.md)（Opus 默认配置）一起并行发起**（不在此处硬编码模型名与参数）。
   - 当方案足够复杂、双路存在分歧或主控（Controller）信心不足时，主控可按需启用 [`dsh-review`](../dsh-review/SKILL.md)（`dsh.py task` / `start`）作为第三路独立意见。
2. **独立审查，严禁预设主控立场（防诱导）**：
   - 无论是在向 Codex 和 Opus 征集方案构思，还是请他们审查方案/代码，传入的 Prompt **只准包含客观问题现象、用户原始诉求、相关源码路径、变更范围与项目阶段约束**。
   - **严禁把当前主控自己的倾向性立场、辩解、预设结论或引导性假设塞进征询/审查 Prompt**，避免引导外部模型顺着主控思路附和（即使当用户明确要求“把你的方案给他们审一下”时，也只客观陈述待审方案内容与验收要求，不预设主控方案必然正确的立场）。
3. **单方不可用时自动切换兜底**：
   - 双路并行时若 Codex 或 Opus 任一方不可用（CLI/认证/配额/连接或执行故障），**默认自动启用 [`dsh-review`](../dsh-review/SKILL.md)（`dsh.py task` / `start`）补位以尽量保持双路独立意见**并在汇总表注明；若用户明确只指定了单一方且不可用，则自动切换到另一可用方继续完成审查并说明。

## 模式 A：三方方案共创与“防过度设计”体检

1. **并行发起同题外部只读征询（不做分工式拆问，保留交叉印证）**：
   - 当存在显著影响实现路径的未决假设、关键契约取舍或瓶颈归因不明时，整理一份中立背景文件（含项目上下文、当前阶段原则与相关代码/契约位置），**向 `codex-task`（Codex 默认配置）与 `opus-task`（Opus 默认配置）发送完全相同的核心 Prompt**（避免“一方只算 ROI、一方只查契约”导致失去双路交叉验证），同时主控自己独立完成一份构思。
   - **中立三档评估要求（防倾向性引导）**：在 Prompt 中要求外部模型依据用户已确认目标、当前阶段约束与有出处的契约（附具体文件路径/测试名），**对等比较「不改 / 缩小范围最小改动 / 拟议方案」三档结论**的收益、实现及验证成本与风险；允许有证据地建议“不实施”（缺少实测数据时不虚构收益比例），且不论结论档位如何，均须给出满足目标的最小可行替代方案供用户决策。
2. **汇总输出固定四要素（先结论后细节）**：
   - **① 三方共识与分歧对比表**：清晰列出主控、Opus、Codex 各自方案的核心机制、优缺点与分歧点，供用户拍板。
   - **② 成本与阶段估算**：给出各方案/阶段的改动范围、开发与回归验证成本估算，判断适合一口气做完还是分阶段推进。
   - **③ 「防过度设计」砍削清单**：对照当前项目阶段目标与实际约束，砍掉不必要复杂度（不降低已确认的验收标准与安全隔离边界）：
     - 能否用纯前端/确定性代码解决，避免额外增加 LLM 调用或延长时延？
     - 能否复用现有组件/字段（如原生 `placeholder`、现有 facts），避免新建后端 API、数据库表或通用核验平台？
   - **④ 架构/流程对比图（仅限架构或数据流变更时）**：当方案涉及跨服务/跨模块职责或流式管线结构调整时，附上独立的「修改前 vs 修改后」架构图或流程图；纯局部改动不画多余图表。

## 模式 B：独立 Worktree 双写赛马（A/B Implementation）

**触发条件**：当用户明确要求“赛马 / 让 Codex 同时在独立 worktree 开发一份”，或遇到**存在两种及以上合理实现路径、仅靠静态讨论难以取舍的设计不确定问题**（含后端状态机/架构取舍，或需要两套 UI/交互视觉方案对比）时使用（若仅是风险高但改法明确的单一路线修复，优先采用“主控单写 + 补单测 + 双路外审”，避免双写拉长端到端耗时）。

1. **对齐同一基线与合同（自适应开启浏览器视觉与本地运行能力）**：
   - 锁定同一个基准 commit（如当前 `master`）与完全相同的需求计划、输入样本、门禁与验收标准。
   - 当前主控在自身 worktree 实施候选 A；通过 [`codex-task`](../codex-task/SKILL.md)（使用默认 Codex 配置）在另一个独立 git worktree 实施候选 B（保持同组件单写者，互不干扰）。
   - **无需用户额外叮嘱“看画面”，始终自适应启用能力**：只要任务涉及前端 UI、页面交互、图表渲染或本地运行验证，派发 Codex 任务时**默认自动附带 `--write --host-access --authorization "在独立 worktree 改码、启动独立端口本地服务并用 Playwright 浏览器（zh-CN）截图与 view_image 视觉自检"`**，让 Codex 自主起服务、截屏并用 `view_image` 看画面闭环，绝不盲写 UI。
2. **交叉互审 + 独立双审**：
   - 双方实现并通过项目契约测试与单测门禁后，先交叉比对两份 `git diff`，再调用 [`opus-review`](../opus-review/SKILL.md) 与 [`codex-review`](../codex-review/SKILL.md)（使用各自默认配置，复杂或低信心时主控可加开 DSH 第三路）对 A、B 两份实现进行不预设主控立场的独立盲评（若某一方不可用则自动由可用通道完成）。
3. **实证择优与整合**：
   - 以实际测试通过率、边界安全性、代码精简度与真机浏览器（`zh-CN`）实测截图择优（不按模型名气定结论）。
   - 吸收另一方的优点合入胜出版本，重跑验证并展示关键 case 的实测截图。
